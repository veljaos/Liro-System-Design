# Document

Producing something the user takes out of the system: a PDF, a printout, a
preview, a file on disk.

Colour: `liro-violet`. Nothing changes in the database; something leaves the
screen.

## Intents in this family

| Intent | Default label | Weight | Confirms |
|---|---|---|---|
| `pdf` | PDF | `filled` | no |
| `print` | Print | `filled` | no |
| `preview` | Preview | `light` | no |
| `download` | Download | `light` | no |

## When to use

- **`pdf`** — generates the document as a PDF, usually for sending or archiving.
- **`print`** — sends it to a printer, or opens the browser's print dialogue.
- **`preview`** — shows what the output will look like, without producing a file.
- **`download`** — saves an existing file to disk. The file already exists; this
  action does not create it.

## When not to use

- **Not for exporting a list to Excel.** That is `excel`, in `positive`. The
  distinction is what is being produced: `document` produces a **document** —
  something with a layout, meant to be read or filed. Excel produces **data**,
  meant to be worked on further. They are different acts and belong in different
  families.
- **Not for sending.** A PDF that a user downloads has not gone anywhere. As soon
  as it goes to a client or an authority, it is `send` in
  [verify](verify.md).
- **`download` is not `pdf`.** If the button generates the file, it is `pdf` even
  when the browser then downloads it. `download` is for a file that already
  exists — an attachment, a bank statement, an archived filing.
- **Not for a report that is being run.** Producing a report is work with a
  duration and a result; that is a job, and it belongs to `JobProgress` and
  `submit`, not to a document button.

## How it behaves

`pdf` and `print` are **`filled`**. `preview` and `download` are `light`.

None of the four asks for confirmation. Nothing here changes a record, and a PDF
generated by mistake costs one click to discard.

## Examples

A document screen, where producing the output is one of the things the user came
for:

```tsx
<ActionGroup>
  <ActionButton intent="preview" />
  <ActionButton intent="pdf" />
  <ActionButton intent="send" />
</ActionGroup>
```

An attachment row, where the file already exists:

```tsx
<ActionGroup>
  <ActionButton intent="download" iconOnly />
  <ActionButton intent="delete" iconOnly />
</ActionGroup>
```

Producing a document that takes time:

```tsx
<ActionButton
  intent="pdf"
  loading={generating}
  label={{ en: 'Generate PDF' }}
/>
```

`loading` rather than a disabled button with a spinner elsewhere: the button that
started the work is where the user looks for the result.

## Why it is like this

**Why `pdf` and `print` are filled.** This is the one place in the system with
**two filled buttons on the same screen** on purpose, which reads as a
contradiction of rule 4 in `AGENTS.md` ("one filled button per screen").

The reason is recorded in `intents.ts`: in Liro Business App, PDF and print are
among the most frequent actions on a document screen. An accountant looks for
them before anything else. A light violet button next to a filled blue one gets
lost, and the most-used action on the screen ends up being the quietest.

The rule is not abandoned — it is applied where it matters. On a screen where
`pdf` is filled, the primary action usually is not: a posted invoice has no
"Save". When both appear, the screen has genuinely two things a user comes to do,
and pretending otherwise helps nobody.

**Why violet and not neutral.** Producing a document is not administration. It is
the point of the record: an invoice exists in order to be issued, a filing in
order to be submitted. Grey would put it beside "Filter" and "Refresh", which is
where it does not belong.

**Why nothing here confirms.** None of the four changes state. This is the family
where the cost of a mistake is one wasted click, and it is worth noticing that the
system uses confirmation sparingly precisely so that it still means something when
it appears — see [destructive.md](destructive.md).
